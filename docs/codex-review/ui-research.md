# MatchLens UI research and review — pass 1

2026-10-27. Scope: static code comparison against `all-features`, the existing redesign research and reviews, selected saved screenshots, and current primary-source documentation. I did **not** run the app or observe the present runtime; the old fan/coach review findings below are historical reports to retest, not claims of current defects. `ui-redesign-codex` began at `afbea45`; other agents may change the code after this snapshot.

## Recommended demo priorities

1. **P0 — Make Broadcast a first-class, low-friction destination.** `frontend/src/lib/routes.ts` points at `/explore/broadcast`, and `frontend/src/features/explore/explore-page.tsx` only renders its tile when `!coachMode`. The primary nav and command palette contain Explore but no Broadcast command. The screen itself is intact (`frontend/src/app/explore/broadcast/page.tsx`: full-screen monitor, exit, copy link and optional sound), and `frontend/next.config.ts` redirects legacy `/broadcast` to it. Restore a clearly labelled entry from Live or shared navigation and a command-palette destination; ensure it remains available in coach mode. Keep the clean output, legacy redirect, and shared match context. Verify entry, exit, copied URL, playback and mobile/keyboard controls in a running app.
2. **P0 — Make one match moment the story across audiences.** Start with match, score, clock and a clear replay/synthetic indicator, then show a meaningful moment with a plain-language explanation and an obvious evidence/details action. Offer Broadcast and Coach views of the same state without resetting playback. The seeded scorer correction (`dataset/ml-demo-001/events.jsonl`, events `ml-demo-001-e01123` and `ml-demo-001-e01124`) is a high-value trust demonstration: show old attribution, corrected attribution and which outputs updated only if the current pipeline actually produces those results. Do not imply video auto-detection or live real-world data. Verify the precise moment and propagation before presenting it as implemented.
3. **P0 — Trust must agree across surfaces.** The earlier coach review reported conflicting recommendations and raw, confusing correction and yellow-card text; its test was on a prior running build. Retest current state. A correction should identify the field changed and the event/time, with evidence and current state rather than a cryptic name swap. A recommendation must not be highlighted as a winner when the verdict says no clear winner. Show meaningful unavailable, stale, loading, empty and failure states; avoid implied confidence not supported by data.
4. **P1 — Surface useful actions where users need them.** Put catch-up and pundit near the match context; link to moments, relevant stats and a Broadcast view with verb-led labels. Keep the visible navigation small, but do not make a search shortcut the only discovery method. Make replay pace and paused/live status legible beside the clock, and do not let floating actions obscure match data at narrow widths. Preserve settings and state while navigating.
5. **P1 — Make each lens answer a real question.** Fan: “What happened, and why does it matter?” Coach: “What should I do and what evidence supports it?” Enthusiast: “Which players, events and numbers explain this?” Use one shared scoreboard and event identity, contextual drill-down, labeled units, and honest limitations. Prefer xG with a short explanation rather than labeling a fractional expected-goals value as a count of chances. At FT, direct a coach to the report and avoid presenting in-match recommendations as actionable.

## Perspective review

- **Fan:** Score/clock and named moment should be instantly readable; “Catch me up” should reveal then/now score and a few checked developments. Full-time empty or zero-vote polls should not compete with the story. Give xG a simple explanation, make mobile cards full width, and retain user-selected language and narration across views. Earlier fan review reported a clipped carousel, overlapping action pill and opaque-menu issues; recheck rather than assume they still reproduce.
- **Coach:** Show phase, team selection, actionable recommendation, its confidence and evidence timestamp together. If the game is finished, show the report, not a tactic to execute. Keep uncertainty and the overall verdict consistent. Prior coach review also reported thin player statistics, collapsed shot markers and contradictory tactic verdicts; subsequent redesign work may have changed them. Validate with a half-time and FT dataset before promising a bench-ready workflow.
- **Enthusiast:** Provide quick paths from a moment to player/shot details, chronological timeline, team comparison, and xG/momentum context; show source, units and timing for derived metrics. Retain accessible filters and direct links so this is more than a decorative live feed. A confidence badge alone is insufficient without a way to inspect the data behind it.

## FotMob and frontend evidence

The saved FotMob teardown (`docs/redesign/fotmob-teardown.md`) documents 1440px and 390px captures: stable home-left/away-right comparison, score and match context above clear tabs, contextual stat help, click-through shot details, and an events timeline. The prior report describes measured interface behavior; I did not recapture FotMob myself. The official [FotMob match page](https://www.fotmob.com/matches/malaga-vs-al-arabi/2vaft3a) confirms its coverage combines live events, xG, momentum, shot maps, lineups and commentary; its list establishes available features, not independent proof of ease of use. Adapt hierarchy and quick drill-down, not its branding or licensed assets. The inspected saved MatchLens screenshot `docs/redesign/screens/after/round-3/coach-overview-1440.png` shows a persistent scoreboard, team selector, Coach tabs, readable recommendations and a side-by-side match graph; this is a historical screenshot, not a current browser observation.

Installed `frontend/package.json` identifies Next 16.4.2, React 19.3.0, Tailwind 4 and Base UI 1.9.0. The current [Next.js App Router navigation guide](https://nextjs.org/docs/app/getting-started/linking-and-navigating) documents `Link` prefetching, client transitions, and `loading.tsx` for dynamic routes. Use established links and appropriate loading feedback instead of adding a new navigation framework. `frontend/AGENTS.md` requires implementers to consult the installed Next documentation before code changes. Keep semantic links/buttons, focus indication, keyboard operation, adequate touch targets and reduced-motion handling; test rather than assume these properties.
